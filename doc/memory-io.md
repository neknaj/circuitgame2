# 外部 I/O とメモリの仕様

ルート回路と外付けデバイスの接続規則を定義する。接続の指定は[プロジェクト設定](project-config.md)、デバイスの挙動は[内蔵 RAM](simulation.md#状態素子)と[標準デバイス](peripherals.md)を参照する。

## main のポートへの割り当て

通常は `main` を実行するルートモジュールとして選ぶ。別のルートを使う場合は実行設定で選択する。外部から扱うピンは、選択したモジュールが宣言した名前付きの入出力ポートである。1ビットの信号も複数ビットのバスもポートとして扱う。接続の記述は実行設定に置く。同じ `main` にテスト用メモリと実際に永続化するメモリを差し替えられる。

| 接続 | デバイス側の操作 |
| --- | --- |
| `main` の `out` | 確定した出力値を読む。複数のデバイスが同じ出力を観測できる |
| `main` の `in` | 次に適用する入力フレームの値を決める。各入力ポートに駆動元を1つ割り当てる |

初版はポート単位で名前を対応させ、方向と型・ビット幅の一致を検査する。入力への重複接続はエラーとし、未接続の入力は実行環境が与える入力フレームで扱う。デバイスへの割り当てがあるポートをテストや UI から直接駆動する場合は、その実行の接続設定で入力源を切り替える。

## 外付けインターフェイスの関数

外付けインターフェイスは型付きポートと接続するユーザー定義の状態遷移である。入力はインターフェイス自身の状態、直前の tick で確定した回路出力、その時点までにホストから渡されたイベントである。戻り値は次の状態、今回の tick に渡す回路入力、ホストへ出す要求の有限列とする。例えばフラッシュのインターフェイスは、回路出力のアドレスと制御ビットを解釈して読み出しを要求し、後続の tick でホストから受け取った応答を回路入力に変換する。キーボードのイベントを回路入力に変換する処理や、回路出力を画面表示用のデータに変換する処理も同じ形で書ける。

遷移関数の型は次の形を取る。`State` とポートの型はインターフェイスの定義で決まる。

```text
step(State, CircuitOutputs, TickContext, List<HostEvent>)
  -> Result<(State, CircuitInputs, List<HostRequest>), InterfaceError>
```

`TickContext` は今回確定する論理 tick、reset の世代、設定されている場合は tick 周期を持つ。時刻はこれらの論理値から求める。ファイル、ブラウザの永続化、画面への描画はホストが実行する。応答を待つ操作の成功・失敗は後続のイベントとして渡す。[デバイス契約](device-contract.md)が初期化、イベントの型、応答の照合を定める。回路のコンパイル時、外付けインターフェイスの実行時、テスト時で組み込み関数を切り替え、tick の進行はホストが管理する。

外付けインターフェイスも [`run_slice`](macros.md#一時停止再開中断) で実行する。全デバイスは同じ確定済みの回路出力を読む。すべての遷移と回路の更新が成功したときに、tick、回路とデバイスの新状態、イベントの消費を一括で確定し、要求をホストへ一度だけ渡す。一時停止からの再開では途中状態を使う。確定前にエラーや中断が発生した場合は、その tick の途中状態を破棄して最後の確定状態に戻り、当該 tick のイベントと要求は未消費・未発行のままとする。装置の応答が求められる時刻とハンドシェイクは[tick ごとの受け渡し](#tick-ごとの受け渡し)に従う。

## tick ごとの受け渡し

tick `t` の開始時に、デバイスは tick `t-1` の終了時に確定した回路出力と、今回受け取ったホストイベントを読む。デバイスが算出した入力フレームと確定済みの回路出力を使い、要求側と応答側それぞれで `valid == 1` かつ `ready == 1` なら転送が成立する。送信側は成立まで `valid` とデータを保持する。tick `t` で受理した要求の応答は、最短で tick `t+1` の入力に載る。回路出力が tick `t` の終了時に変わった場合、その値をデバイスが読むのは次の tick である。

初期の要求・応答型デバイスは同時に1件の要求を扱う。ホストは tick の開始時にイベント列を確定し、一時停止からの再開でもこの列を使う。適用 tick を指定しないライブ入力と応答は、イベントを受け取った後で入力がまだ確定していない最初の tick に適用する。到着順はホストが直列化して記録する。

テストと再生では、各イベントに reset 世代、適用 tick、同じ tick 内の順序を指定する。応答の適用 tick には対応する要求の確定より後の tick を指定する。指定された応答が届くまで待つ実行では、その tick の開始前に待つ。応答を待っている間は直前の状態を観測できる。テストでは固定の応答列か、同じポート規則を持つメモリ上のデバイスを使う。

## 外付けメモリ

外付けメモリは[純粋関数型言語](macros.md#外付けインターフェイス)で記述できる。アドレス、データ、制御信号をどう解釈するか、読み出し・書き込み・消去の条件、待ち時間、アドレス範囲外の応答、reset の効果を、デバイス自身の状態遷移として定義する。例えば、揮発性のテスト用 RAM は内容も状態として持てる。フラッシュやファイルを使うメモリは、ホストへの要求と応答によって内容を管理する。大きな試験用 RAM でも、状態の意味論に従う範囲で実装は配列の全コピーを省ける。

例えば8ビットデータのフラッシュ読み出し口は、次のように割り当てられる。方向は `main` から見た方向である。

| `main` のポート | デバイスのポート | 方向と幅 |
| --- | --- | --- |
| `mem-address` | `address` | `out` 16ビット |
| `mem-req-valid` | `req-valid` | `out` 1ビット |
| `mem-req-ready` | `req-ready` | `in` 1ビット |
| `mem-rsp-valid` | `rsp-valid` | `in` 1ビット |
| `mem-rsp-data` | `rsp-data` | `in` 8ビット |
| `mem-rsp-error` | `rsp-error` | `in` 1ビット |
| `mem-rsp-ready` | `rsp-ready` | `out` 1ビット |

書き込みや消去を扱うデバイスは、操作種別と書き込みデータを要求チャネルに追加する。

| tick | フラッシュ読み出しの例 |
| --- | --- |
| `t` | 確定済みの出力で `mem-req-valid = 1`、今回の入力で `mem-req-ready = 1`。メモリがアドレスを受理し、tick 確定時に読み出し要求をホストへ渡す |
| `t+1` | 応答データが利用可能であれば `mem-rsp-valid = 1` とデータを入力に載せる。回路の確定済みの `mem-rsp-ready` が0なら転送は成立せず、デバイスは応答を保持する |
| `t+2` | `mem-rsp-ready = 1` になった場合、保持していた応答の転送が成立する |

上の例の reset 後は、次の入力フレームで受付可能・応答なしを返す。未処理の応答と世代の管理は[デバイスの初期化とリセット](device-contract.md#初期化とリセット)に従う。確定済みの永続化操作はホストのデバイス仕様に従う。

要求・応答のハンドシェイクは [Arm の AMBA AXI 仕様](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf)を参考にした。
