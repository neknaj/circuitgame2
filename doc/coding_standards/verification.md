# Verus による形式証明の実装方針

プロジェクトが各段階で証明する性質は [Verus による検証設計](../verification.md)に従う。この文書では仕様を Verus のコードに表し、実装と証明を変更する手順を定める。

## 仕様と実装

変更に着手するときは、対応する仕様の節、対象となる入力、公開 API が保証する結果を確かめる。認識関係、型付け、状態遷移は `spec` で記述し、検証対象の `exec` 関数の返り値から独立して定義する。証明を組み立てる補題は `proof` とし、通常ビルドと Verus で同じ `exec` コードを使う。

`requires` は呼び出し側が満たす条件、`ensures` は実装が保証する結果を書く。上限を設ける場合は対象と理由を明示し、文法違反、値の範囲外、資源上限を区別する。`recommends` は `requires` と同じ強制条件ではない。添字などに必要な条件は、仕様の関係式でも明示する。

契約が受理すべき入力まで拒める形になっていないかを確認する。例えば厳格パーサーでは成功した AST の文法適合と入力末尾までの消費に加え、文法上正しい入力を規定範囲内で受理することを示す。回復側では妥当な入力で厳格側と同じ AST を返し、読み飛ばした範囲と合成位置を区別する。診断はエラー種別に対応する根拠を仕様から定義する。

### 未検証の呼び出し側

通常の Rust ビルドでは `requires` は実行時に検査されない。CLI、LSP、WASM との境界など、未検証の呼び出し側に公開する API では、事前条件ごとに次の方法を選ぶ。

- 前提を型に持たせる。例えば解析結果から取得したハンドルで対象を指定し、別の構文木の添字を渡せないようにする。
- 渡された値を実行時に検査し、範囲外や前提違反を `Option` または `Result` で返す。外部入力や古い文書版から前提違反が起こり得る場合は、この方法か型による保証を使う。
- 呼び出し側のプログラム上の誤りとしてパニックを許す場合は、発生条件を `# Panics` に記す。その API を外部入力から呼ぶ境界では、必要な条件を先に確かめる。

### 仕様が意味のある条件を表すことの確認

重要な公開契約では、通常の入口から仕様の前提である `requires` を満たす入力が得られることを確認する。例えば型検査済みの式を対象にした定理なら、利用側が型検査の戻り値から定理の前提を導けることを確かめる。代表例の期待結果が仕様を満たすことを確認する。具体値で判定できる `spec` には `assert(...) by (compute)` を使える。一般の保証は全対象を覆う定理で示す。

契約をレビューするときは、正常な入力を拒否する、返すべき値を落とす、診断や修復を空にするといった誤結果を、その契約が排除できるか確認する。必要に応じて、誤結果が述語を満たさないことを `proof` で示すか、隔離した作業ツリーでその誤りを入れた実装が Verus に拒まれることを確かめる。例えば回復パーサーでは、返した修復に根拠があることに加え、報告すべき修復や後続の正常フォームを落とせないことを確認する。

下位の処理が証明した性質は、それを使う公開 API の事後条件や補題までつなげる。高速経路には、安全に使える条件と、採用した場合の参照経路との結果の一致を記す。仕様が条件を満たす入力で高速経路を使うよう要求する場合は、その条件から経路の選択を導けることも確認する。実際の処理量や環境ごとの速度は計測する。

## 不変条件と停止性

不変条件は初期状態で成立し、各反復で保存され、終了時に事後条件を導く形にする。`decreases` に減少する量を書く。例えば、残りトークン数と解析スタックの未終了枠数を辞書式に減らす回復規則は、[診断と補完](../diagnostics.md)に定める。

`exec` の減少量の検査は、呼び出し先の停止を前提に、対象のループや再帰が停止することを調べる。停止性を報告するときは、呼び出し先の停止も証明した範囲と、呼び出し先の停止を前提として残した範囲を明記する。

局所的な事実はアサーションや補題で示し、公開契約までつなげる。例えば1回の字句分割で正確な接尾辞が得られる証明は、字句解析全体が元入力を欠落や重複なく覆う証明に使う。

## 高速化で保つ性質

高速版を実装する前に、参照版と共有する仕様と、公開 API から観測できる結果を定める。成功と失敗の条件、成功時の値とその順序、失敗時の診断を含める。実装ごとに表現が異なる場合は、平坦な索引から各定義の参照列を取り出す例のように、仕様に対応する値への射影を定義する。

両実装が独立した仕様を満たし、同じ入力から得られる公開結果が一致することを Verus で示す。仕様の一意性から一致を導く場合は、その一意性も証明する。共有処理を使う場合は、索引の収集や高速経路の選択が公開結果に影響しないことを、呼び出し側で使える契約にする。高速経路を使えず参照版に切り替える場合も、同じ契約を満たすことを示す。

厳格解析では、受理・拒否、最初に選ぶ違反、およびそのエラー値全体を対象とする。エラー種別、主範囲、関連範囲を仕様で決める。例えば余分な閉じ括弧が続く場合、先頭の余分な閉じ括弧を選ぶ根拠まで示す。回復解析では、妥当な入力での厳格解析との一致と、異常な入力で報告する診断や修復の根拠を [診断と補完](../diagnostics.md) に従って示す。

## 証明とテストの役割

Verus で表現できる core の仕様適合や実装間の一致は、公開契約と証明で保証する。代表的な受理例・拒否例は、仕様の意図を確認する回帰テストとして残す。公開 API の使用例は通常の Rust ビルドでコンパイル・実行する。生成入力を使う差分テストは全体検査で実行する。証明範囲を報告するときは、未証明の性質を明示する。

テストを見直すときは、各アサーションが確かめる性質を、対応する公開契約と照合する。一つのテストが、証明済みの一致と公開 API の動作の両方を確かめることもある。実行頻度や残す例は、それぞれのアサーションの役割から決める。

対象環境でのビルドや、CLI の出力、LSP ホストの文書版の扱いなどは、対応する実行環境や結合テストで確かめる。編集の途中は変更箇所に対応する検査を選び、仕様・契約・実装を変更した節目では Verus を実行する。節目の全体検査では全テストと対象環境向けのビルドを実行する。

## 仮定とレビュー

証明すべき事実を `assume` で置いたり、検証対象の本体を属性で検査から外したりしてはならない。外部コードとの境界に仮定が必要な場合は、対象と適用範囲、仮定する契約、その理由、依存する公開定理を記録する。`vstd` が外部に与える仕様に依存する場合も、変更のレビューで必要な契約を確かめる。

CI で Rust ソースを `git grep` などで検索し、次の構文の追加を検出する。レビューでは実際の構文と適用先を確認し、禁止された用途や記録のない仮定を修正する。検索結果にはコメントや文字列も含まれ得るため、該当箇所を確認する。

- `assume`。証明すべき事実を仮定する文。
- `#[verifier::external_body]` と `#[verifier::external_fn_specification]`。検証しない本体や、検証外の実装について仮定した契約。
- `#[verifier::external]`。検証対象から外す宣言や実装。関数の場合は `external_body` などを経由する間接依存を確認する。トレイト実装の場合は、型検査を通じて検証結果へ影響し得る点も確認する。
- `verifier::exec_allows_no_decreases_clause`。関数、モジュール、クレートに適用できる、実行コードの減少量検査を外す属性。検査を外すときは、理由と停止性を前提とする範囲を記録する。

追跡済みの Rust ソースを検索する例を示す。

```sh
git grep -n -w -E 'assume|external_body|external_fn_specification|external|exec_allows_no_decreases_clause' -- '*.rs'
```

レビューでは仕様、実行コード、証明、仮定を照合する。正常例と異常例で仕様自体の妥当性を確認する。固定したツールチェーンで `cargo verus verify --locked` と対象の Cargo テスト・ビルドを実行し、どの契約が証明され、どの動作をテストで確認したかを報告する。
