# Verus による検証設計

## 方針

`no_std + alloc` の core が通常のビルドで実行するコードを、パーサーから VM、言語サービス、マクロ評価器まで Verus で検証する。公開仕様として守る性質を先に記述し、実装の成功条件、適用範囲、利用者が観測する結果を定理にする。個別のループやデータ構造に付ける証明は、公開の保証を導くために使う。

| 層 | 証明する性質 |
| --- | --- |
| 字句解析 | 各トークンが対応する UTF-8 の範囲と字句規則を満たす。空白やコメントを含めた区間が元の入力を重複や欠落なく覆う |
| 厳格パーサー | 成功した AST は独立した文法仕様に従い、入力末尾まで消費する。文法が許す入力は、明記したサイズ・深さの範囲内で受理する。構文エラー、範囲外の数値、資源上限を区別する |
| エディタ向けパーサー | 正しい全文を与えた場合に厳格パーサーと同じ AST を返す。回復の各操作で未処理トークン数または解析スタックの枠が辞書式に減り、実在する範囲と合成した欠落位置を区別する |
| 名前解決と型・結線検査 | 各参照がそのスコープの束縛を指し、ポート幅、スライス範囲、フィールド配置、単一駆動を満たす。回路定義の再帰を拒否し、ゲートを経由するワイヤのフィードバックを許す。仕様上型が一意に決まるプログラムは、資源上限内で受理する |
| 展開とネットリスト生成 | 束縛、ポート順、ビット順、状態素子のインスタンスを保存する。`func` では任意の合法な入力に対する出力値を、`module` では入力列に対する tick ごとの観測結果を保存する |
| VM と状態素子 | 初期化と各 tick が参照仕様に一致する。ラッチの保持、RAM の読み出しと書き込みの順序、非対象アドレスと他インスタンスの値の保存を示す |
| 純粋関数型評価・マクロ展開 | 型検査と循環検査を通った関数の停止、一時停止と再開を挟んだ評価の一致、展開先に対応する構文、識別子の束縛と展開位置を保証する |
| 外付けインターフェイス | 1回の遷移関数の停止、ポート型への適合、同じデバイス状態・回路出力・論理時刻の情報・イベント列から同じ結果を得ること、確定前の失敗や中断でイベントを消費せず要求も渡さないことを示す。[外部 I/O の仕様](memory-io.md)と[評価器の仕様](macros.md)を参照する |
| 言語サービス | [診断と補完](diagnostics.md#形式的な契約)が確定した根拠と制約に適合する。正規化済みの有効位置で位置変換が往復し、定義への移動がコンパイラと同じ束縛を指す |

字句規則・文法は認識関係として、型付けと名前解決は判断規則として記述する。回路の評価は出力値または状態遷移を与える仕様として記述する。これらの定義は実行用関数の返り値を参照せず、その関数を使わずに読んでレビューできる形にする。停止性は入力位置や作業量の減少を呼出先も含めて示し、深い構文と大きな展開ではホストの呼び出しスタックに依存しない実装を選ぶ。関数型評価器の fuel は一時停止の間隔を決める。受理されたプログラムが停止することは、fuel の総量に依存しない定理として示す。

## 編集単位の増分解析

同じスナップショットについて、増分解析とキャッシュを使わないエディタ解析が、同じ問い合わせと解析段階で同じ診断・補完・定義位置を返すことを示す。比較には構文エラーの回復結果と、未解決の参照を含める。妥当な入力では、共通の解析対象について厳格なコンパイラ解析との一致も示す。

字句・構文結果の再利用では、再開位置までの結果が維持されること、接尾部に合流するときの継続状態が、回復中の未確定な構文も含めて等しいこと、再利用した範囲が新しい文書内の同じテキストを指すことを示す。意味解析の再利用では、記録した依存先の値がすべて等しければ問い合わせの結果が等しいことを示す。名前解決の未解決結果、宣言の追加・削除、設定やソース集合の変更もこの契約に含める。プロトコル経由の複数編集の順序、取り消し、公開時の文書版の照合はホストとの結合テストで検査する。

## コンパイルの正しさ

最初の定理はマクロを含まない正しく型付けされた回路を対象とする。解析、型・結線検査、型付き回路からのネットリスト生成、VM 実行の定理を順に合成する。構文レベルの型や名前を消去する際は、消去前の型付き回路とネットリスト上の対応表を仕様に用いる。スライスでは選んだ各ビットの順、`struct` では各フィールドのオフセットと空きビット、RAM では独立したインスタンスへの対応を確認する。

`func` の定理は、任意の合法な入力を与えたとき、ソースの組み合わせ評価と生成したネットリストの評価の出力値が一致することを主張する。`module` では、階層を保ったソース上の回路に tick の参照意味論を定義する。内部で使う `func` の組み合わせ出力を一括評価すると伝搬時間が変わるため、その演算を構成する各基底ゲートの状態を参照意味論にも含める。ネットリストとの間に状態の対応関係を定め、reset で成立すること、同じ入力フレームによる1 tick の遷移で保存されること、対応する状態から同じ観測値が得られることを示す。これらから任意の有限入力列に対する trace の一致を導く。対象の観測値には公開ポートの値と、外部から読み取れると宣言した VRAM の内容を含める。外部デバイスとの比較には同じ入力フレーム列を与える。

最適化の許可条件も二つに分ける。`func` 単体では出力値の保存を求める。`module` の内部と、そこで使う `func` の特殊化には tick ごとの観測値の保存を求める。例えば NOR による二重否定を直結に置き換えると、組み合わせ評価では同じ値を返すが、順序回路では2ゲート分の伝搬が消え、reset 直後や入力を切り替えた直後の trace が変わる。この操作は `func` の単体評価用に限定し、`module` 用の展開では、定理で許可できる変換を使う。

[利用者による回路の証明](circuit-proofs.md)では、コンパイラと VM の意味保存に使う参照意味論を外部の Verus クレートから参照する。

## 証明の採用とレビュー

証明を追加する際は、守る契約とその契約が防ぐ実装上の誤りを対応させる。例えば、パーサーの AST に妥当なインデックスが入る性質は文法への適合や入力の完全消費と結び付ける。試験で見つけた誤動作は、契約の不足であれば契約を改め、実装の誤りであれば契約に従う実装へ直す。仕様と実装が同じ手順をなぞるだけの定理、実際の API から到達できない前提の下だけで成立する定理、既存の型が保証する性質の言い直しだけを、公開の保証として数えない。

Verus を適用する各層の CI では、実行用コード、公開定理、証明が置く仮定をレビューする。仮定を追加する場合は、該当箇所、必要性、その仮定に依存する定理を記録する。ホストのファイルシステム、永続化デバイス、未検証のライブラリや外部コードの性質は、仮定または統合テストとして扱う。パーサーやコンパイラを `assume` や `external_body` で済ませ、その結果を証明済みとして扱う運用は認めない。通常のビルドと Verus で共通の実行コードを使う。文法、回路仕様、観測点などの仕様自体が意図どおりであることは、具体例、異常系テスト、仕様レビューで確認する。

実装順序は[ロードマップ](design.md#実装順序)を参照する。ここに掲げる定理は検証計画であり、実装と証明結果は core のコードと CI で確認する。

定常化の自動解析では検証済みとして返す上界と周期が、参照ステップに対する契約を満たすことを Verus で示す。ゲート深さの計算では、ゲートごとの深さと入力信号の深さの関係を検証し、最大深さを上界とする定理につなぐ。状態遷移の展開による検査を加える場合は、制約が同じ参照ステップから生成されることと、反例の再生が不一致を示すことを検証する。外部ソルバーが反例なしと返した結果を保証に用いる場合は、ソルバーが生成した証明書を検査するか、そのソルバーを信頼する前提を明示する。
