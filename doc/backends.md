# GPU と RP マイコンの実行バックエンド

## Core との接続

NCG2 のプロジェクトはホストで解析し、配線・型・資源の上限を検査してから対象に渡す。既存の CPU 実装を参照とし、バックエンドの公開結果を Core の回路と tick の意味論に対応させる。対応外の素子やポート構成があれば、実行前に対象と理由を報告する。外付け I/O の要求、応答、reset 世代の扱いは既存のデバイス契約に従う。 [シミュレーション](simulation.md) · [外付けデバイスの契約](device-contract.md)

## PC の GPU

wgpu の compute shader で、同じ回路に対する独立した入力列をまとめて実行する。最初は NOR のみの回路を対象とし、CPU の u64 ビットスライス版と同じレーン順・ビット順を使う。GPU 内部のレーンは WGSL の u32 に詰める。u32 の各ビットが同じ入力と状態を持つ1ケース分の Core の結果と一致することを Verus で示す。シェーダー実行とドライバー、転送経路は GPU での差分検査に含める。組み合わせ回路はレーンの各ワードがゲートを依存順に評価する。順序回路では現在のゲート出力を読み、次の出力へ書く。バッファーを tick ごとに交換して、同じ tick の更新を先に読み込むことを防ぐ。 [wgpu の compute dispatch](https://wgpu.rs/doc/wgpu/struct.ComputePass.html#method.dispatch_workgroups)

ネットリストと実行中の状態は GPU に置き、入力をまとめて転送する。出力列を要求する場合は、その範囲をまとめて読み戻す。実行規模は NOR ゲート数、独立したケース数、tick 数、dispatch 回数、転送量を記録する。比較では CPU のビットスライス版と出力が一致することを確認し、全体の所要時間と GPU の計測値も併記する。小さいバッチから始めて、転送を含めて GPU が有利になる規模を実機で測る。ラッチと RAM は状態とインスタンス分離を比較できる段階で追加する。

## RP2040・RP2350

初版は Raspberry Pi Pico と Pico 2 の ARM ビルドを対象とする。ホストで検査した回路とポート割り当てからボード向けの実行イメージを作り、マイコン上で tick を進める。ボード設定には使うピン、方向、周辺機能の番号、通信の条件を記す。ピンの重複と周辺機能に割り当てられないピンを起動前に検査する。 [Raspberry Pi のマイコン仕様](https://www.raspberrypi.com/documentation/microcontrollers/microcontroller-chips.html) · [GPIO と周辺機能](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html)

| 接続 | 初版の動作 |
| --- | --- |
| GPIO | tick の開始時に入力ピンを読み、確定した出力をピンに反映する。入力と出力のピン、初期出力レベルを指定する |
| UART | ハードウェア UART でバイト列を送受信する。baud と 8N1 を設定し、受信データ・フレーミングエラー・受信あふれを次の利用可能な tick へ渡す |
| SPI | ハードウェア SPI をコントローラーとして使い、クロック、モード、ビット順、CS を設定する。送信と同時に受信したデータを要求への応答として返す |
| I²C | ハードウェア I²C をコントローラーとして使う。7ビットアドレス、読み出し、書き込み、反復 START を使う書き込み後の読み出しに対応し、NACK などは型付きの応答で返す |

同じ回路を複数ケース実行する場合は RP の32ビット演算で状態を詰め、Core のレーン射影の証明を使う。物理ピンはボード設定で接続した一つの実行に対応させる。通信の完了待ちは tick の評価処理から外し、完了後に要求 ID と reset 世代を照合して応答を届ける。バッファーの上限、タイムアウト、tick 周期を守れなかった場合の診断を定める。物理ピンを回路で直接切り替える用途は GPIO の経路を使う。バイトやトランザクションを渡す用途は専用周辺機能を使う。回路が作った高速波形を直接送受信する用途は、必要な分解能を満たせるかを PIO を含めて別途検証する。

検査ではまず記録した入力と周辺機能の応答から、CPU 参照版と各 tick の出力を照合する。両ボードをビルドした上で、GPIO の折り返し、UART の送受信、SPI の送受信、I²C の読み書きと NACK をそれぞれ実機で確認する。マイコンの処理量は対象回路のゲート数、tick 数、送受信バイト数、利用可能な場合はサイクル数を記録する。

### GPIO の配線表

ボード固有の設定は、通常の `circuitgame2.toml` とは別の TOML ファイルに書く。`board` で `"pico"` または `"pico2"` を選び、`[[gpio]]` ごとに GP 番号の `pin`、ルート回路の単一ビットポート名 `port`、回路側の `direction`（`"input"` または `"output"`）を指定する。出力の `initial_high` は省略すると false。

各回路入力には GPIO を一つ割り当てる。同じ回路出力は別々のピンへ送れる。未接続の出力も回路の公開出力順に残る。設定の並びを変えても、配線表の回路入力と公開出力は宣言順で、同じ出力の接続先は設定順になる。周期はプロジェクトの `tick-ns` から取り、マイクロ秒の正の整数で正確に表せる場合に使う。

`ncg2 rp-plan` は回路と割り当てを検査してから配線表を標準出力へ書く。検査で失敗した場合は配線表を出力しない。ファームウェアのビルドは配線表とボードの組を検査する。CPU・GPU と同じ tick の意味論を使い、実機の GPIO の電圧とタイミングはボード上で確認する。 [GPIO のサンプル](https://github.com/neknaj/circuitgame2/tree/main/examples/rp-gpio)

### I²C の配線表の設計

ボード設定の `[i2c]` では、`instance` にコントローラー番号、`sda-pin` と `scl-pin` に GP 番号を指定する。`frequency-hz` は `100000` または `400000`。`timeout-micros` は1取引の待ち時間を正の整数マイクロ秒で指定する。GPIO と合わせてピンの重複と周辺機能への割り当てを検査する。初版で使う回路ポートは単一ビットとする。複数のビットを使う項目はポート名を配列に並べる。

| 回路から見た方向 | 信号 | 意味 |
| --- | --- | --- |
| 出力 | `request-valid`、`address`、`write-length`、`read-length`、`write-data` | 7 ビットのアドレスに対する取引。二つの長さはそれぞれ8ビット |
| 入力 | `request-ready` | 要求を1件受け付けられる |
| 入力 | `response-valid`、`response-status`、`read-data` | 完了した要求の結果。状態は成功と失敗の理由を区別する |
| 出力 | `response-ready` | 回路が応答を取り込む |

整数は最下位ビットから並べる。送受信データはバイト順に並べ、各バイトも最下位ビットを先頭にする。I²C の配線上の順序はコントローラーに従う。配線表で扱うデータ領域の容量はバイト単位で定め、長さの型で表せる255バイトを上限とする。送信データの先頭から書き込み長で指定されたバイト数を送る。読み出し長より後ろの受信領域と、失敗した応答の受信領域には0を出す。

応答状態は3ビットで、0は成功、1は要求の長さ違反、2はアドレス NACK、3はデータ NACK、4は調停敗北、5はバスエラー、6はタイムアウト、7はコントローラーの再初期化が必要な状態を表す。

長さが0の側は省略する。両方の長さが正なら、「書き込み、反復 START、読み出し」を1回の取引として扱う。両方が0、またはいずれかが容量を超える要求には、物理転送を開始せずに異常を返す。この応答も、要求を受け付けた tick の次の tick 以降に提示する。

デバイスは前の tick の確定済み出力を読む。要求を受理した tick が確定してから通信タスクへ渡し、応答を要求 ID と reset 世代で照合する。応答は入力がまだ確定していない最初の tick から提示し、応答 ready が立つまで内容を保持する。通信エラーの場合は原因を応答に載せる。バスを再利用できることが確認できるまで新しい物理転送を止める。 [外付けデバイスの tick ごとの受け渡し](memory-io.md#tick-ごとの受け渡し)

ボード設定に誤りがあれば、該当するポート名やピンの位置を診断に載せる。複数の設定が同じ入力を駆動する場合は、両方の設定位置を示す。回路側の型や方向が合わない場合は、設定位置と回路側の宣言位置を示す。
