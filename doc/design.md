# circuitgame2 設計

circuitgame2 は S 式で記述した論理回路を CLI と Web で同じ tick の規則に従って実行する。設計段階の仕様を扱う。初版の対象と候補は各文書で示す。

## ソース形式

| 拡張子 | 言語 | 内容 |
| --- | --- | --- |
| `.ncg2` | Neknaj Circuit Game 2（NCG2） | 論理回路、状態素子、回路テスト、マクロの呼び出し |
| `.ncg2m` | Neknaj Circuit Game 2 Meta Language（NCG2M） | マクロの定義、外付けデバイスの状態遷移、プロパティテストの関数 |

両言語は S 式の字句解析と[名前解決](names.md)を共有する。

## リポジトリと依存関係

| リポジトリ | 責務 |
| --- | --- |
| [circuitgame2](https://github.com/neknaj/circuitgame2) | `doc/` の仕様、共通サンプル、期待する出力・trace、リリースの組み合わせを検査する CI |
| [circuitgame2-core](https://github.com/neknaj/circuitgame2-core) | Rust の構文解析、型・結線検査、ネットリスト、VM、テスト実行、エディタ向け言語サービス、純粋関数型の評価器、Verus の仕様と証明 |
| [circuitgame2-gui](https://github.com/neknaj/circuitgame2-gui) | ブラウザの実行画面と WASM バインディング。エディタ、可視化、永続化、ネイティブ GUI も段階的に担当する |
| [circuitgame2-cli](https://github.com/neknaj/circuitgame2-cli) | Rust のコマンド、診断表示、ファイル入出力、ネイティブと WASI の実行環境、LSP サーバーの通信・プロトコル変換 |
| [circuitgame2-editors](https://github.com/neknaj/circuitgame2-editors) | Neovim と VS Code の拡張、エディタ別のパッケージ作成、LSP サーバーとの互換性テスト |
| [circuitgame2-lib](https://github.com/neknaj/circuitgame2-lib) | NCG2 の汎用回路と NCG2M の補助関数。利用側のプロジェクトに組み込むソースとして配布する |

GUI と CLI は core に直接依存する。メインの統合 CI は各リポジトリのコミットを指定してチェックアウトし、共通サンプルを検査する。core 内のライブラリや証明は必要に応じて Cargo workspace 内のクレートに分ける。メイン、core、GUI、CLI、editors、lib の6リポジトリで構成する。editors は CLI が配布する `circuitgame2-lsp` を LSP 経由で利用する。エディタ固有の設定や配布を変更したときは、editors から対象の拡張だけを更新できる。

## 実装の境界

core は `#![no_std]` と `alloc` を使用する。構文木、診断、ネットリスト、VM 状態は動的な容量を使い、実行環境がアロケータを提供する。構文解析とロード、VM の状態遷移とホスト I/O はそれぞれ別の API とする。core は UTF-8 の入力、型で検査した回路、入力フレームを受け取り、診断と状態遷移の結果を返す。エラー種別は `enum`、ソース位置は span で表し、文面と表示は CLI と Web が担当する。OS 依存のファイル、時計、乱数、Canvas API はアダプターに置く。Web では VM 状態を WASM 側に保持し、描画はコピーした観測値から作る。

初版の基底ゲートは2入力 NOR とする。ラッチと RAM は VM の状態素子として実装し、RAM はホスト配列を用いて容量に比例するゲートの展開を避ける。ホスト配列は[状態素子の仕様](simulation.md#状態素子)に従う。ゲートで構成したラッチを自動置換する場合は、保存する観測結果と変換条件を検証する。外付けデバイスとファイルや描画の副作用は[外部 I/O](memory-io.md)に従って扱う。配線遅延や電気特性はシミュレーションの対象外とする。

マクロ評価器では純粋な結果を保ったまま一時的な記憶領域を再利用する [FBIP の試作](development.md#マクロ評価器の高速化)を行う。最初は所有が一意なバッファを対象とし、[評価と再開の仕様](macros.md#一時停止再開中断)に適合することを検証する。

## 実装順序

| 段階 | 完了条件 |
| --- | --- |
| 1. 構文と組み合わせ回路 | [字句、S 式、回路フォーム](grammar.md)に従うパーサーを実装し、AST との対応を Verus で示す。ネイティブと WASM で同じ core をビルドする。メモリ上の複数ソースから宣言を集め、名前空間、公開、完全修飾名、別名の衝突を検証する。小さな `func` で型・結線検査から出力値の保存までを示し、複数出力、スライス、struct へ広げる |
| 2. 順序回路と RAM | `module-part` の全断片を一つの回路に組み立てる。SR ラッチ、発振器、RAM の初期化、同アドレス読み書き、インスタンス分離を trace で検査する。reset と1 tick の対応を示し、出力列の保存を導く。ゲート専用の非循環回路について[定常化の上界を推定](static-analysis.md#自動解析)する |
| 3. CLI・Web・LSP | ネイティブ CLI、WASI CLI（`wasm32-wasip2`）、Web の出力列を比較する。外部 I/O は[実行設定](project-config.md)と固定の応答列で接続を検査する。TOML のソース設定を CLI・Web・LSP に接続する。回路言語の共通プロジェクトで、Web のスイッチ、LED、tick 操作、CLI の定常化検査、各エディタの診断・定義参照・定常化のインレイヒントを検査する。回路言語のエラー回復、診断、補完の契約を Verus で検証する。段階1の組み合わせ回路が完成した後に、段階3で回路言語の[編集単位の増分解析](development.md#編集単位の増分解析)を実装し、差分テストと全体解析との一致証明を追加する |
| 4. 純粋関数型言語 | 両ソース形式を同じプロジェクトで解決し、停止性と再開、マクロの束縛、I/O の確定と中断を検証する。増分解析を含む言語サービスを関数型言語とマクロを含む文書へ広げ、生成元を示す診断を検証する。生成テスト、ユーザー定義の外付けデバイス、[標準デバイスと描画](peripherals.md)を実装する |

## 実装前に決める事項

| 項目 | 決める時期 |
| --- | --- |
| UART 以外のデバイスごとのオプションとホストイベント・要求の型 | 各外付けデバイスの実装前 |
| NCG2M の式・データ型の完全な文法、構文の分解と反復ごとの新しい束縛の生成 | 段階4の型検査と幅に応じたマクロ生成の実装前 |
| ユーザー定義デバイスの登録、状態・ポート・イベント・結果を構築して分解する型と操作 | 段階4の外付けデバイスの実装前 |
| プロパティテストの入口、入力列生成、型付き trace、失敗例の保存形式 | 段階4の生成テストの実装前 |
| 周期条件を宣言するソース注釈の採否と、フィードバック回路に対する検査方式 | 非循環回路の自動解析と条件を受け取る CLI の実装後 |
